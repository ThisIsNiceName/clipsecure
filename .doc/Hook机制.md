# Hook 机制：由浅入深，以及 Linux 与 Windows 的差异

这份说明回答两个问题：介绍 Hook 时可以按什么顺序讲、能讲清哪些点；ClipSecure 在 Windows 上用 Detours 拦截剪贴板 API，同样的做法在 Linux 上是否成立。

先给结论。

Hook 由浅入深，是「改动离原函数越来越近、覆盖的调用越来越多、对二进制和权限的依赖越来越重」。介绍一份机制时，把层次、覆盖范围、怎样调用原函数、重入和平台差异讲清楚，就够读者判断该停在哪一层。

ClipSecure 的 Detours 不能在 Linux 上直接链接或运行。同类产品效果可以做：参与进程加载自己的 `.so`，在**写入剪贴板时**放上公开占位和私有密文，在**本进程读取时**解密。Linux 没有 `SetClipboardData` / `GetClipboardData` / `CloseClipboard` 这三个固定入口，拦截点要换成该进程实际使用的 GTK、Qt、X11 或 Wayland 接口。

## 1. Hook 在调用链上的位置

### 1.1 三个角色

Hook 是在一条已经存在的调用路径上插入自己的逻辑。调用结束前，可以选择继续进入原实现，也可以改掉参数、返回值或副作用。

一条被钩住的调用里始终有三个角色：

| 角色 | 含义 | 在 ClipSecure 里 |
| --- | --- | --- |
| 调用方 | 业务代码，它以为自己在调用系统 API | 编辑器、业务进程里的复制粘贴 |
| 钩子 | 先执行的函数 | `HookSetClipboardData` 等，负责加解密 |
| 原实现 | 钩子决定放行时调用的函数 | `TrueSetClipboardData` 等，指向原 API |

介绍时先画这张关系，后面每一层都是在回答同一件事：钩子怎样抢在原实现之前运行，以及原实现的地址保存在哪里。

### 1.2 和插件的差别

插件是主程序按约定去加载一个新模块，调用它导出的入口。Hook 是模块插进主程序**已经会调用**的函数。ClipSecure 两者都沾边：SDK 本身要被进程加载进来，加载之后做的事是 Hook，是改剪贴板 API 的走向。

[C++插件机制.md](C++插件机制.md) 里的 `LD_PRELOAD`、`dlopen`、`extern "C"` 会在这里再次出现。插件文档解决「模块如何被装进进程」；这篇解决「装进进程之后，怎样接到既有调用上」。

## 2. 由浅入深的七层

越往下，越不需要目标程序配合，也越依赖二进制布局、内存权限和系统策略。能在上一层做完的事，就不必降到下一层。

| 层次 | 介入时机 | 改的是什么 | 谁会被拦到 | Linux 上的常见做法 | Windows 上的对应物 |
| --- | --- | --- | --- | --- | --- |
| 1. 源码和框架预留 | 编写业务或选用框架时 | 回调、虚函数、模块接口 | 只走这条预留路径的调用 | GTK 模块、Qt 事件过滤器、显式回调 | 窗口过程子类化、COM 接口、官方回调 |
| 2. 链接期包装 | 重新链接目标程序 | 链接器生成的包裹符号 | 该程序里对这个符号的未解析引用 | `ld --wrap`、弱符号 | 链接器 `/ALTERNATENAME`、静态库里的同名符号 |
| 3. 加载期符号抢占 | 进程启动、动态链接器绑符号 | 符号解析顺序 | 动态链接、且经该符号进入的调用 | `LD_PRELOAD`、`dlsym(RTLD_NEXT)` | 没有同等的环境变量；常靠先加载的 DLL 或清单重定向 |
| 4. 改写过程链接表 | 运行中，改本模块的跳转表 | ELF 的 GOT，或 PE 的 IAT | 经过这张表的外部调用 | 改 GOT（Full RELRO 下该表只读） | 改 IAT |
| 5. 内联 Hook | 运行中，改函数体开头 | 目标函数的前几条指令 | 凡是进入这个函数体的调用 | 自写蹦床，或 funchook 一类库 | Microsoft Detours 的 `DetourAttach` |
| 6. 进程外附加 | 另一个进程停住目标 | 目标进程的内存或寄存器 | 被附加的那个进程 | `ptrace` 一类调试接口 | 远程线程、`WriteProcessMemory` |
| 7. 内核与系统策略 | 进入内核的边界 | 系统调用或安全策略 | 真正陷入内核的操作 | seccomp、eBPF、LSM | 对象回调、微过滤驱动、ETW |

下面按这个顺序说明每一层能讲什么。第 6、7 层只保留能力边界：它们管的是调试权限和内核策略，剪贴板内容本身并不住在某一个系统调用里。

### 2.1 源码和框架预留

调用方在源码里写了回调、虚函数或插件入口。Hook 是框架作者留出来的，签名稳定，卸载路径清楚。

这一层覆盖面最小：不走这条回调的代码完全无感。它也最稳，因为不依赖编译器把函数放在哪、指令长什么样。

图形程序里，GTK 的 `GTK_MODULES`、Qt 的事件过滤器和平台插件，都属于框架留好的扩展位。业务愿意改一行代码时，显式调用 SDK 也在这一层，Hook 就没有必要。

### 2.2 链接期包装

目标程序还要重新链接。GNU 链接器的 `--wrap=symbol` 会把对 `symbol` 的引用改到 `__wrap_symbol`，原符号以 `__real_symbol` 留下。弱符号可以让程序在「有实现就用、没有就走默认」之间选择。

这一层适合自己掌握构建的程序。发行给别人的二进制、系统里的 GTK 和 Qt，都不会为了剪贴板 SDK 重新链接。

### 2.3 加载期符号抢占

动态链接器解析符号时，预加载库里的同名符号先被选中。这是 Linux 上与「进程加载我们的库、业务源码不动」最接近的一层，也是 Detours 那种用法在 Linux 上的第一选择。

`LD_PRELOAD=libclip.so` 只影响**之后启动**、并且是动态链接的进程。已经在跑的进程不会因为设置了这个变量而改变。静态链接进去的函数、被编译器内联掉的调用、事先用 `dlsym` 取出并保存的函数指针，都不会再经过这次解析。

钩子里要调用原函数时，用 `dlsym(RTLD_NEXT, "符号名")` 取「搜索顺序里的下一个实现」，避免调回自己。下面用 `puts` 演示这个形态，它和剪贴板无关，只说明抢占和回调用的写法：

```c
#define _GNU_SOURCE
#include <dlfcn.h>

typedef int (*puts_fn)(const char *s);

int puts(const char *s) {
    static puts_fn real_puts;
    if (!real_puts) {
        real_puts = (puts_fn)dlsym(RTLD_NEXT, "puts");
    }
    return real_puts(s);
}
```

C++ 成员函数还会再遇到名称修饰，和[插件一文](C++插件机制.md)里的 `extern "C"` 是同一个问题。Qt 的 `QClipboard::setText` 是 C++ 符号，用环境变量抢占它，要比抢占一个 C 函数更依赖编译器 ABI。glibc 还有符号版本（例如 `GLIBC_2.2.5`），同名函数可能对应多个版本，抢占时要对准调用方绑定的那一个。

### 2.4 改写 PLT/GOT

ELF 里，模块调用外部函数时，先经过过程链接表（PLT），再从全局偏移表（GOT）取出真正的地址。运行中把自己的函数地址写进 GOT，以后这个模块经 PLT 出去的调用会进钩子。

这和 Windows 上改导入地址表（IAT）是同一类手段：改的是**调用方模块里的一张表**，函数体不动。因此：

- 只有走这张表的调用会被拦到。
- 调用方如果已经拿到函数指针，或在本模块内部直接调用，表的内容不影响它。
- 开启 Full RELRO 后，重定位完成，GOT 变为只读。之后再改表，要先处理页权限，并面对此时正在进行的调用。

介绍这一层时，把「表」和「函数体」分开画。ClipSecure 的 README 里写的 IAT 限制，指的就是这一层，见第 4 节。

### 2.5 内联 Hook

内联 Hook 改目标函数开头的指令，让它跳进钩子，再用一段蹦床执行被覆盖的原指令，然后回到原函数剩余部分。原函数地址保存在蹦床里，也就是 ClipSecure 里 `TrueSetClipboardData` 这类指针。

Microsoft Detours 的 `DetourAttach` 做的是这一层：替换目标函数开头，把传入的函数指针改成蹦床。同一进程里，只要执行流进入这个函数体，就会进钩子，包括通过 `GetProcAddress` 取到同一地址再调用的路径。

Linux 上可以做同样的事，但 Detours 这份实现过不去，原因见 [5.1](#51-detours-不能直接使用)。即便换用支持 Linux 的内联库（例如 funchook），仍然要处理：

- x86_64 指令长度不固定，覆盖的字节必须落在完整指令上。
- 位置无关代码、短函数、开头就是跳转的垫片（thunk）。
- 其他线程可能正执行被覆盖的那几条指令。
- 开启 CET / IBT 时，间接跳转的目标需要合法的 `endbr64`，随意写一条跳转会被 CPU 拒绝。
- 代码页同时不可写、可执行。改字节前要调整页权限，改完再恢复。

所以内联 Hook 是「函数指针已经绑死、符号抢占碰不到」时的手段，是 Detours 在 Windows 上的默认手法。

### 2.6 从进程外附加

调试接口可以让另一个进程停住目标、读它的内存。Linux 上这条路受 `ptrace` 作用域约束（Yama 的 `ptrace_scope`）：很多发行版默认只允许调试自己的子进程，不允许随意附加到别人的进程。

ClipSecure 当前没有走这条路。`InstallHooks` 跑在**已经加载 SDK 的那个进程内部**。介绍 Hook 时可以把「进程外附加」标成独立话题：它引入调试权限、审计和目标进程的生命周期，和「业务进程主动加载 SDK」不是同一个部署模型。

### 2.7 内核与系统策略

系统调用过滤（seccomp）、动态探测（kprobes、eBPF）和安全模块（LSM）能在进入内核时记录或拒绝操作。它们适合文件、网络、权限这类确实会陷入内核的行为。

Linux 剪贴板数据放在用户态：X11 的选区由持有它的客户端保存，Wayland 由合成器在客户端之间转交。读写剪贴板通常是套接字上的协议消息，没有一个等于 `SetClipboardData` 的系统调用。把 Hook 做到内核，拦不到「这次复制的是哪一段文本」。

## 3. 一份介绍里可以写清的点

按下面这些问题写，顺序就是从浅到深。每一问都对应上面的某一层，读者能据此选择手段，也能知道手段覆盖不到哪里。

| 要写清的点 | 读者应能回答的问题 |
| --- | --- |
| 定义 | 钩子、调用方、原实现各是谁 |
| 和插件、回调的边界 | 这是框架留的入口，还是后来插进去的 |
| 介入时机 | 编译、链接、加载，还是进程已经跑起来之后 |
| 作用域 | 单个进程、新启动的进程，还是系统里所有进程 |
| 覆盖范围 | 只拦「经过某个符号 / 某张表」的调用，还是「进入这个函数体」的全部门 |
| 原函数怎么继续调用 | 保存的原指针、`RTLD_NEXT`，还是蹦床 |
| 重入 | 钩子内部又调到被钩的 API 时如何避开自己 |
| 线程 | 安装过程中其他线程是否正在执行目标函数；状态放在哪 |
| 卸载 | 能否把指令或表项改回去，何时允许卸载库 |
| 符号与 ABI | C 名字、C++ 修饰名、glibc 符号版本是否一致 |
| 绕过方式 | 静态链接、内联、已取走的函数指针、直接系统调用 |
| 二进制格式 | ELF 的 PLT/GOT，PE 的 IAT，函数体在哪 |
| 内存与 CPU 策略 | RELRO、代码页不可写、CET/IBT 会让哪一层失败 |
| 权限 | 谁允许把代码装进这个进程；进程外附加是否被系统禁止 |
| 可观测性 | 怎样确认钩子装上了、怎样确认走的是原函数 |
| 选型 | 目标进程会主动加载 SDK 时，停在哪一层就够 |

ClipSecure 这种「可信进程自己装 SDK」的介绍，写到第 5 层就够用：第 1 层是能改业务时的首选，第 3 层是 Linux 上不改业务时的首选，第 5 层用来对照 Windows 里 Detours 的做法。第 6、7 层用来说明边界，避免把进程外注入或内核探测当成剪贴板 SDK 的实现路径。

## 4. Windows：Detours 在本项目里做了什么

### 4.1 名字都叫 Hook 的三种手段

Windows 文档里的 Hook 常常指 `SetWindowsHookEx`。它把一个 DLL 挂进图形线程的消息循环，用来看键盘、鼠标或窗口消息。操作系统会按 Hook 类型把 DLL 加载到相关进程。这是消息钩子，不修改 `SetClipboardData` 的指令。

另外两种才和「替换 API 行为」有关：

| 手段 | 改哪里 | 拦到谁 |
| --- | --- | --- |
| IAT Hook | 某个模块导入表里的函数地址 | 只有这个模块通过导入表发出的调用 |
| 内联 Hook | 目标函数开头的指令 | 进入该函数体的调用，含 `GetProcAddress` 得到同一地址后再调用 |

`SetWindowsHookEx` 没有 Linux 等价物。X11 的事件过滤、辅助功能总线（AT-SPI）看起来也在「听输入」，但它们不改剪贴板 API，也不能当成 Detours 的移植方向。

### 4.2 ClipSecure 的实际路径

参与进程加载 SDK 之后，`InstallHooks` 用 Detours 事务安装三个钩子：

- `SetClipboardData`
- `GetClipboardData`
- `CloseClipboard`

`hook.h` 写的是内联 Hook。`src/hook.cpp` 里的调用是 `DetourAttach`，属于上一节的内联 Hook：函数体被改写，`TrueSetClipboardData` 被 Detours 换成蹦床，钩子末尾通过蹦床进入原实现。

仓库 README 写的是「IAT Hook，自行 `GetProcAddress` 或硬编码地址就拦不到」。那是第 4 层改导入表的限制。当前安装路径用的是 `DetourAttach`，作用范围是同一进程里进入这三个函数体的调用。两处说法不一致时，以 `InstallHooks` 的代码为准。

和移植相关的行为还有这些：

- **钩子装在参与进程内部。** 未加载 SDK 的进程不会执行解密逻辑。
- **其他进程看到占位，是因为写入时就放了占位。** `CS_POLICY_DUAL` 在文本路径上调用原 `SetClipboardData` 写入占位，再用自定义剪贴板格式写入密文。旁观进程读标准文本格式，拿到的是占位；同组进程读的时候，钩子发现自定义格式，解密后返回。
- **重入用 TLS 挡住。** 钩子里会再次调用原 API。`TlsGetValue` 为真时直接走原函数，避免加密逻辑套娃。`CloseClipboard` 时清掉「下一次加密 / 解密」的一次性标记。
- **没有去附加别人的进程。** 代码路径里没有 `DetourCreateProcessWithDll` 或远程线程。部署模型和「每个可信进程自己装 SDK」一致。

加密格式、密钥组和占位文案都不依赖 Detours。依赖 Detours 的是「业务仍调用原来的三个 Win32 函数，行为却被换掉」。

## 5. Linux：能否做同样的事

### 5.1 Detours 不能直接使用

仓库里的 `include/detours.h` 和 `detours.lib` 是 Windows 上的 Microsoft Detours 4.0.1。它不能作为 Linux 钩子库使用：

- 头文件和实现依赖 Win32 进程、线程和内存保护接口，目标文件格式是 PE。
- `DetourAttach` 按 Windows 上的指令布局和调用约定生成蹦床，不识别 ELF。
- 剪贴板函数本身是 `user32.dll` 的导出。Linux 进程里没有这个模块，也没有这三个符号。

支持 Linux 的内联库（如 funchook）和 Detours 处于同一层，API 却是另一套，不能把现有的 `DetourTransactionBegin` / `DetourAttach` 调用原样编译过去。即便换了库，要钩的函数也不叫 `SetClipboardData`。

### 5.2 产品效果落在写入的数据上

本项目的可见效果可以拆成两半：

1. 参与进程写入时，公开格式是占位（或按策略只留密文），私有格式是密文。
2. 参与进程读取时，若存在私有格式且密钥组匹配，钩子返回明文。

第 1 点发生在**写入方进程**。其他进程不需要被 Hook，它们只是按普通方式读取公开格式。这一点在 Linux 上同样成立，只是「格式」从 Windows 的剪贴板格式号，变成选择目标或 MIME 类型，例如公开的 `text/plain` 放占位，私有类型放密文。

第 2 点要求**读取方进程**里有 SDK。Linux 上同样是：谁要透明解密，谁就加载 `.so`。不需要、也不应该把钩子铺进系统里每一个进程。

因此 Linux 移植的部署模型和现在一致：可信进程加载 SDK。变化的是 SDK 内部用什么接住「复制」和「粘贴」。

### 5.3 拦截点随图形栈变化

Windows 把剪贴板收成用户态里一组同步 API：打开、写入若干格式、关闭；读取时按格式号取出。数据由系统侧的剪贴板保存。

Linux 桌面没有这一组 API。数据留在提供方，或由合成器转交，请求往往是异步的。

| 进程实际使用的栈 | 写入时常见的接口形态 | 读取时常见的接口形态 | 和 Win32 的差别 |
| --- | --- | --- | --- |
| X11 选区 | 成为 `CLIPBOARD` 选区的拥有者，在 `SelectionRequest` 里按目标提供字节 | 转换选区，在 `SelectionNotify` 里取回 | 没有一次「写入即被系统保存」的调用；提供方要一直应答，直到失去拥有权 |
| GTK 3 | `gtk_clipboard_set_text`、`gtk_clipboard_set_with_data` | `gtk_clipboard_wait_for_text`、按目标请求内容 | C 符号，适合加载期抢占；自定义目标用来放密文 |
| GTK 4 / GDK | `gdk_clipboard_set_text`、`gdk_clipboard_set_content` | `gdk_clipboard_read_text_async` 及完成回调 | 读取是异步的，钩子要接回调，不能假设函数返回时数据已经到手 |
| Qt | `QClipboard::setText`、`setMimeData` | `QClipboard::text`、`mimeData` | C++ 符号，有名称修饰；还要对付内联和库的 ABI |
| Wayland | `wl_data_source` / `wl_data_device` 的协议请求，或桌面门户 | 同一协议的接收端，通常还要求当前有焦点 | 流量在套接字上，不在 libc 的某个剪贴板函数里 |

文件列表、HTML、位图在 Windows 上是 `CF_HDROP`、`HTML Format`、`CF_DIB`。在 Linux 上它们是不同的 MIME（如 `text/uri-list`、`text/html`、`image/png` 或 `image/bmp`），没有 `HGLOBAL` 这种统一外壳。加密载荷可以仍走私有 MIME，序列化格式可以沿用现有头部设计，但喂给钩子的缓冲区类型要按协议重写。

`CloseClipboard` 在 Linux 上没有对应函数。现在用它清除一次性的加密/解密标记；移植时要把这个标记的生命周期绑到「一次设置」或「一次读取请求」的结束，而不是绑到一个关闭调用。

Wayland 还有产品层的差别：很多合成器只允许当前焦点客户端读取剪贴板。后台进程不能像 Windows 服务那样随时 `GetClipboardData`。这缩小了旁路读取的范围，也让「任意进程装上钩子就能读剪贴板」不成立。

### 5.4 建议停在哪一层

参与进程会加载 SDK 时，按这个顺序选：

1. **业务能改调用点：** 直接走 SDK API，不 Hook。这是第 1 层。
2. **业务不能改，但进程用 GTK 等 C 接口：** 用 `LD_PRELOAD` 或框架自己的模块机制抢占那几个 C 符号，在钩子里写占位和私有 MIME，并用 `dlsym(RTLD_NEXT)` 调用原实现。重入保护改用线程局部存储，对应现在的 TLS 槽。这是第 3 层，和当前「进程自己装 SDK」的部署方式一致。
3. **符号已经绑死，或调用在 C++ 运行库内部：** 再考虑 PLT/GOT 或内联 Hook。这一层要单独处理 RELRO、指令长度和 CET，不能从 Detours 移植。
4. **希望以后启动的程序都经过同一套策略：** 当前代码的部署方式是每个可信进程自己加载 SDK。若要覆盖未加载 SDK 的程序，X11 上要另外做一个选区剪贴板管理器，Wayland 上则依赖合成器提供的数据控制协议。这两条都是剪贴板协议里的客户端，在协议消息中处理 MIME。

静态链接的程序、以及把剪贴板逻辑编进自己二进制的运行时，第 3 层覆盖不到。这和「调用没有经过被钩函数」是同一类缺口，需要在支持范围里写明图形栈，而不是承诺一个全局剪贴板钩子。

### 5.5 对照

| 维度 | Windows（本仓库当前实现） | Linux 上的同类做法 |
| --- | --- | --- |
| 钩子库 | Microsoft Detours 4.0.1 | 不能使用这份库。加载期用动态链接器；必须改函数体时另选内联库 |
| 安装位置 | 已加载 SDK 的进程内部 | 相同：已加载 `.so` 的进程内部 |
| 代码里的手法 | `DetourAttach` 内联 Hook | 优先符号抢占；内联只处理抢占不到的函数 |
| 剪贴板入口 | `user32` 的三个同步 API | 由 X11、Wayland、GTK、Qt 决定，没有固定三函数 |
| 数据放在哪 | 系统剪贴板按格式号保存 | 提供方或合成器按 MIME / 选区目标保存 |
| 其他进程看到占位 | 写入时已经提交占位格式 | 写入时提交公开 MIME 的占位 |
| 同组进程看到明文 | 本进程读钩子解密私有格式 | 本进程读路径解密私有 MIME |
| 调用原实现 | Detours 蹦床（`True*` 指针） | `dlsym(RTLD_NEXT)` 或内联库的蹦床 |
| 重入 | Windows TLS | 线程局部存储 |
| 一次性标记的边界 | `CloseClipboard` | 一次设置或一次异步读取的结束 |
| 已运行进程 | 当前代码不会附加到别的进程 | `LD_PRELOAD` 同样只作用于之后启动的动态链接进程 |
| C++ 接口 | Win32 这些 API 是 C 符号 | Qt 一类接口带名称修饰，抢占成本更高 |

## 6. 小结

介绍 Hook，按七层从预留回调讲到内核策略即可。每一层写明改的是回调、符号、跳转表还是函数体，谁会被拦到，原函数如何调用，以及重入和卸载。对本项目，写到内联 Hook 就能和 Detours 对齐；进程外附加和内核探测用来划定边界。

Linux 可以做出同样的产品效果：可信进程加载 SDK，写入公开占位和私有密文，读取时在本进程解密。Detours 和 `user32` 的三个函数都不能直接搬过去。实现时应先用加载期符号抢占或图形框架自己的模块机制，接住该进程真实使用的剪贴板接口；MIME 类型对应现在的自定义剪贴板格式，线程局部存储对应现在的 TLS 重入保护。
